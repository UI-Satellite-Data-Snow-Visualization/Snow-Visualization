## Choosing the FDL start date (D04, D16)

- April 1 (DOY 91, from the starter code) can be a poor start. The team showed 2022, with a median melt-out of April 2. He thinks 2022 was a drought year with an early, compressed melt, and suggested checking SNOTEL stations in the basin for that spring.
- **Near-term suggestion:** use the basin's SNOTEL stations, especially low-elevation ones that melt out first. Find peak snowpack and start about **a week before** it, so no part of the watershed has already melted out on the start date.
- **Longer-term idea:** for each pixel, find the **longest continuous period of snow cover** through the season (roughly February to July) at the chosen threshold. Then derive a start date for the watershed, for example a median, and test whether low and high elevations need different start dates.
- He asked the team to look for a **computationally efficient** method and balance accuracy against cost, possibly using a subset of pixels. The work only has to be done once per threshold, plus once a year for new data. He compared the cost to NSIDC's daily gap-filling, which already runs per pixel worldwide.
- Known complications he raised:
  - over large areas (e.g. the Cascades against high Idaho ranges), melt starts at different times;
  - evergreen forest can make snow look partial or absent to MODIS.
- He asked whether processing each daily image separately or as a stacked 3-D array (days × rows × columns) makes a difference. The current code already uses the 3-D stack.

## Visualizations he'd like (D17)

He asked the team to avoid too much scope creep, and gave this as an incomplete list:

1. **Per-year melt-date maps side by side** (as in the current figure), saved each year so anyone can retrieve and compare them.
2. **The PC1 map** of the recurring pattern.
3. **An advanced page** to compute PC1 for a custom set of years (e.g. drought years only, or high-snowpack years) and **download the GeoTIFF**. Comparison tools aren't needed.
4. **Daily snow cover with clouds filled in using PC1** (the stretch goal).
5. **Snow line under cloud.** When clouds hide the snow line on a day, so no snow pixel is seen next to a land pixel:
   - show the lowest contour where snow is seen ("hard snow") and the highest where land is seen ("hard land");
   - mark the band between them as unknown;
   - overlay the previous day's snow line if it was visible.

   This needs a way to decide whether a usable snow line is visible, e.g. a minimum length in pixels. He suggested RCDS could help with these displays. A team member suggested estimating the hidden snow line from nearby visible pixels instead of only using the previous day's line; both can be compared.
6. *Nice to have:* a semi-transparent **3-D stack of daily snow maps through the melt season** ("a cone that expands outward"), to compare how different years melt. Example: 2011, a low-snow winter followed by heavy snow from late March to late April, with melt lasting into August.

**Expo:** a live demo on a laptop or larger screen, plus a **backup video** in case the live demo fails. Another snapshot day is in December.

## Gap-filled data and Cloud_Persistence

- Using NASA's gap-filled MOD10A1F for FDL/LDS is fine. He recalled that PC1 from last-day-snow and from first-day-land correlated at about "99.999%". The 2019 paper reports **99.8%**; the same recall came up on October 1. Either way, using gap-filled data doesn't materially change PC1.
- The `Cloud_Persistence` layer (days since a pixel was actually seen) matters for **displaying** the snow line, i.e. telling observed from filled pixels. It doesn't for calculating FDL/LDS.

## VIIRS (D02, D03)

- **Pull some VIIRS data early,** even while developing with MODIS, to find out whether the code can stay generic or has to split. He expects the calculations not to depend on resolution (MODIS 500 m, VIIRS about 375 m), only the pixel count.
- MODIS's orbit is decaying and its data quality will decline; VIIRS (from 2012) is its replacement.
- He wants **both sensors offered**:
  - a VIIRS PC1 built from 2012 onward;
  - a user toggle for MODIS, VIIRS or both;
  - with both, the two maps side by side for visual comparison, not pixel-by-pixel matching.
- **MODIS end of life:**
  - when NASA stops producing MODIS data, the tool should tell the user plainly that it's no longer available;
  - an administrator (e.g. RCDS) should be able to mark MODIS as ended from a given date;
  - it shouldn't switch automatically on a short NASA outage.

  A team member noted the date picker should only offer each sensor's available date range.

## Team discussion after the sponsor left

- **Snow-line display:** read as elevation contours for "hard snow" and "hard land", with the unknown band between them; a search along the boundary was suggested to trace it. **Correction:** someone said each MODIS pixel carries elevation data. It doesn't: MOD10A1F has no elevation layer (checked 2026-10-06). An external DEM such as USGS 3DEP or SRTM, put on the MODIS grid, would be needed.
- **VIIRS:** the `uint8` guard (PR #45) confirmed the VIIRS `NDSI_Snow_Cover` layer is also stored as uint8. Nothing else about VIIRS has been checked yet. **Correction:** the starter code's problem was described as converting to a 32-bit integer. It decoded the data to 32-bit **floating point**, which turned fill codes into NaN and then FDL = 0, and used 4× the memory.
- **Repository structure:** separate front-end and back-end repositories, or one repository? It was pointed out that two services can be deployed from one repository, especially if they're containerized, which is the plan. Not decided.
